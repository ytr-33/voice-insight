# 要件定義マルチエージェント(Claude Code 版)

入力素材(要求メモ・議事録・既存資料)から要件定義書を生成する、役割分担型の構成です。
**ヒアリング → 構成設計 → 作成 → レビュー** の4役を司令塔(スラッシュコマンド)が統括します。

## ファイル構成

```
.claude/
├── skills/requirements/
│   ├── SKILL.md                      共有の作法。各役が同じ基準を見るための要
│   └── references/
│       ├── required-inputs.md         入力チェックリスト+穴の2分類(ヒアリング役)
│       ├── document-structures.md     複数ファイル分割パターンのカタログ(構成設計役・作成役)
│       ├── template.md                要件定義書の章立て(作成役)
│       └── quality-checklist.md       品質採点+指摘フォーマット(レビュー役)
├── agents/
│   ├── requirements-clarifier.md      ヒアリング役(読み取り専用 / opus)
│   ├── requirements-architect.md      構成設計役・複数ファイル化の方針を決める(読み取り専用 / opus)
│   ├── requirements-writer.md         作成役(書き込み可 / sonnet)
│   └── requirements-reviewer.md       レビュー役(読み取り専用 / opus)
└── commands/
    └── requirements.md                司令塔。/requirements で起動
```

## セットアップ

1. この `.claude/` を対象プロジェクトのルートに置く(既存の `.claude/` があればマージ)。
2. そのディレクトリで Claude Code を起動する。skills / agents / commands は自動認識されます。
   （ファイルを直接置いた場合はセッション再起動で読み込まれます。`/agents` 経由なら即時。）

## 使い方

```
/requirements 入力素材のパスや要点をここに渡す（例: docs/kickoff-memo.md と議事録）
```

司令塔が回す流れ:

1. ヒアリング役が入力の穴を検出 →「人間への質問」と「仮定ログ」を出す
2. 質問があれば**あなたに提示して一旦停止**(本人にしか分からない事項を捏造しないため)
3. 構成設計役が規模を見て単一/複数ファイルの**文書構成計画**を決める
4. 作成役が計画とテンプレートに沿ってファイルを起草
5. レビュー役が品質基準＋ファイル横断整合で採点(致命0で合格)
6. 不合格なら指摘を作成役に戻して修正 → 再レビュー(最大3回)
7. 確定版・残った未決事項・適用した仮定を報告

## 複数ファイル化について

1ファイルだと全体を浅く書きがちなので、規模に応じて分割します。
`references/document-structures.md` に小/中/大規模の分割セットを用意しており、構成設計役がプロジェクトに合わせて選びます。
横断ドキュメント(非機能・用語・制約・トレーサビリティ・未決事項)は重複を避けるため集約し、ID はファイルをまたいで一意にします。
小規模なら設計役が「1ファイルで十分」と判断することもあります(過剰分割の防止)。

## エージェントごとのモデル指定

サブエージェントの frontmatter に `model:` を1行足すだけです。指定できる値:

- エイリアス: `opus` / `sonnet` / `haiku` / `fable`
- 完全なモデルID: 例 `claude-opus-4-8`、`claude-sonnet-4-6`
- `inherit`: メインセッションと同じモデル(省略時の既定値)

例:

```markdown
---
name: requirements-reviewer
description: ...
tools: Read, Grep, Glob
model: opus
---
```

### このキットの既定と推奨

| 役 | 既定 | 理由 | コスト重視なら |
| --- | --- | --- | --- |
| ヒアリング(clarifier) | opus | 抜け漏れ検出は判断が重い。見逃しのコストが高い | sonnet |
| 構成設計(architect) | opus | 出力は短いが影響が大きい。安く済む | sonnet |
| 作成(writer) | sonnet | 生成量が多くトークンの主因。品質/コストの均衡点 | sonnet |
| レビュー(reviewer) | opus | 粗探しの精度が全体の質を決める。ここは妥協しない | sonnet |
| 司令塔(コマンド) | — | スラッシュコマンドは**メインセッションのモデル**で動く | — |

司令塔だけは frontmatter で指定できません(コマンドはメインセッションが実行するため)。
コーディネートも強くしたいなら `claude --model opus`、通常は `claude --model sonnet` で起動します。

最高難度の判断を詰めたい場合、レビュー/ヒアリングを `fable`(Opus 上位)にする手もありますが、コスト/速度は上がります。

### モデルをまとめて切り替える小技

- 全サブエージェントのモデルを一時的に上書き: 環境変数 `CLAUDE_CODE_SUBAGENT_MODEL` を設定。
- 解決順は「環境変数 → 呼び出し時指定 → frontmatter の `model` → メインセッションのモデル」。
- 推論をさらに深めたい役には `effort: high`(low/medium/high/xhigh/max)も併用できます。

## 設計上のポイント(なぜこの形か)

- **ヒアリングを作成から分離**: 作成役に穴の検出を兼任させると、指摘せずもっともらしい要件で埋めてしまう(抜け漏れの隠蔽)。専任のほうが容赦なく検出する。
- **構成設計を独立**: 「どう分けるか」を書く前に決める役を置くことで、1ファイルに詰め込んで浅くなる問題と、過剰分割の両方を防ぐ。
- **穴の2分類**: 推測で埋めてよい穴は「仮定ログ」に明示してレビューで検証。本人にしか分からない穴は人間に質問(=人間チェックポイント)。
- **レビュー・ヒアリング・設計は読み取り専用**: 成果物を誤って書き換えないようツール権限を絞る。
- **司令塔はメインセッション**: サブエージェントは(原則)他のサブエージェントを呼ばない前提で、反復ループは `/requirements` 経由でメインセッションが回す。

## 注意

- サブエージェントは呼ぶたびにコンテキストが白紙。必要な情報は呼び出しプロンプトに毎回含める設計にしてある。
- サブエージェント多用＋opus多めはトークン消費が大きい。最大反復回数(3回)を守り、必要に応じてコスト重視列に倒す。

## 次の一手

`references/template.md`(章立て)・`document-structures.md`(分割)・`quality-checklist.md`(採点)を
自組織の要件定義標準に寄せると4役そろって精度が上がります。
まず1案件で回し、レビューが取りこぼした観点をチェックリストへ追記して育てるのが定石です。
