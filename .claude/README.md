# 要件定義マルチエージェント(Claude Code 版)

入力素材(要求メモ・議事録・既存資料)から要件定義書を生成する、役割分担型の構成です。
**ヒアリング → 作成 → レビュー** の3役を司令塔(スラッシュコマンド)が統括します。

## ファイル構成

```
.claude/
├── skills/requirements/
│   ├── SKILL.md                      共有の作法。3役が同じ基準を見るための要
│   └── references/
│       ├── template.md               要件定義書の章立て(作成役が読む)
│       ├── required-inputs.md         入力チェックリスト+穴の2分類(ヒアリング役が読む)
│       └── quality-checklist.md       品質採点+指摘フォーマット(レビュー役が読む)
├── agents/
│   ├── requirements-clarifier.md      ヒアリング役(読み取り専用)
│   ├── requirements-writer.md         作成役(書き込み可)
│   └── requirements-reviewer.md       レビュー役(読み取り専用)
└── commands/
    └── requirements.md                司令塔。/requirements で起動
```

## セットアップ

1. この `.claude/` ディレクトリを、対象プロジェクトのルートに置く(既存の `.claude/` があればマージ)。
2. そのディレクトリで Claude Code を起動する。
   skills / agents / commands は配置すると自動的に認識されます。

## 使い方

```
/requirements 入力素材のパスや要点をここに渡す（例: docs/kickoff-memo.md と議事録）
```

司令塔が次の流れを回します。

1. ヒアリング役が入力の穴を検出し、「人間への質問」と「仮定ログ」を出す
2. 質問があれば**あなたに提示して一旦停止**(本人にしか分からない事項を捏造しないため)
3. 回答後、作成役がテンプレートに沿って `requirements.md` を起草
4. レビュー役が品質基準で採点(致命0で合格)
5. 不合格なら指摘を作成役に戻して修正 → 再レビュー(最大3回)
6. 確定版・残った未決事項・適用した仮定を報告

## 設計上のポイント(なぜこの形か)

- **ヒアリングを作成から分離した理由**: 作成役に穴の検出を兼任させると、穴を指摘せず
  もっともらしい要件で埋めてしまう(抜け漏れの隠蔽)。「穴探し専任」を立てるほうが容赦なく検出する。
- **穴の2分類**: 推測で埋めてよい穴は「仮定ログ」に明示してレビューで検証。
  ステークホルダーにしか答えられない穴は人間に質問する。ここが**人間を挟むチェックポイント**になる。
- **レビューとヒアリングは読み取り専用**: 成果物を誤って書き換えないようツール権限を絞っている。
- **司令塔はメインセッション**: サブエージェントは他のサブエージェントを呼べないため、
  反復ループは `/requirements` コマンド経由でメインセッションが回す。

## 注意

- サブエージェントは呼ぶたびにコンテキストが白紙。必要な情報は呼び出しプロンプトに毎回含める設計にしてある。
- サブエージェント多用はトークン消費が大きい。最大反復回数(3回)を守ること。

## 次の一手

`references/template.md`(章立て)と `quality-checklist.md`(採点基準)を、
あなたのドメインや組織の要件定義標準に合わせて書き換えると、3役そろって精度が上がります。
まず1案件で実際に回し、レビュー役が拾えなかった観点があればチェックリストに追記して育てていくのが定石です。
