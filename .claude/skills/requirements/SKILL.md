# 要件定義スキル

このスキルは「要件定義をどう作り、どう疑い、どう検証するか」という**作法を1か所に集約**したものです。
作成・ヒアリング・レビューの3エージェントが**同じ基準**を見ることで、観点のズレを防ぎます。

## 中核となる考え方

良い要件は次の性質を満たします(レビューはこれを基準に粗探しします)。

- **一意**: 要件ごとに ID を持ち、重複しない
- **明確**: 「適切に」「迅速に」「など」のような曖昧語を排除し、可能な限り定量化する
- **検証可能**: その要件を満たしたか後でテスト/確認できる(受け入れ基準が書ける)
- **実現可能**: 制約(予算・期日・技術)の範囲で実現できる
- **必要**: ビジネスゴールに辿れる(トレーサビリティがある)
- **一貫**: 他の要件と矛盾しない
- **完全**: 機能・非機能の主要カテゴリに穴がない
- **仮定の明示**: 確証なく埋めた箇所は「前提・仮定」として明記され、隠蔽されていない

## いつ・どの参照ファイルを読むか(プログレッシブ・ディスクロージャ)

タスクに応じて、必要な参照ファイルだけを読み込んでください。

- `references/template.md` — 要件定義書の章立てテンプレート。**作成エージェント**が起草時に使う。
- `references/required-inputs.md` — 起草前に揃っているべき入力のチェックリストと、
  穴の2分類(推測で埋めてよい / ステークホルダーにしか答えられない)。**ヒアリングエージェント**が使う。
- `references/quality-checklist.md` — 完成ドラフトを採点するチェックリストと、
  指摘の出力フォーマット・合格基準。**レビューエージェント**が使う。

各エージェントは自分の担当する参照ファイルを `Read` で直接開いて従うこと。

## ワークフロー上の位置づけ

1. ヒアリング → 入力の穴を検出(人間への質問 + 仮定ログ)
2. 作成 → テンプレートに沿って起草・修正(仮定を明示、ステークホルダー判断は捏造しない)
3. レビュー → 品質基準で採点し、重大度付き指摘を返す
4. 司令塔(`/requirements` コマンド)が 2↔3 を合格まで反復し、人間質問では一旦停止する
