# 要件定義書テンプレート

作成エージェントはこの章立てに沿って起草する。各章の意図を守ること。
不明な点は捏造せず、「前提・仮定」または「未決事項」に逃がす(後述)。

## 0. 文書管理情報
版数 / 作成日 / 作成者 / 承認者 / 改訂履歴。

## 1. 背景・目的
- 解決したい課題、現状の問題
- このシステム/機能で達成したいビジネスゴール(できれば指標で)
- 「なぜ作るのか」が読んで分かること

## 2. スコープ
- **対象範囲**: 今回扱うもの
- **対象外**: あえて扱わないもの(ここを書かないと後で揉める)

## 3. ステークホルダー
利用者・依頼元・承認者・運用者など。役割と関心事を簡潔に。

## 4. 用語定義
ドメイン用語・略語の定義。読み手による解釈ブレを防ぐ。

## 5. 業務要件 / 主要ユースケース
誰が・どんな状況で・何を達成したいか。代表的な業務フローやユースケースを記述。

## 6. 機能要件
- 要件ごとに **一意な ID**(例: FR-001)を付ける
- **優先度**を MoSCoW(Must / Should / Could / Won't)で示す
- 1要件1文を原則とし、曖昧語を避け検証可能に書く
- 各要件に **受け入れ基準**(満たしたと判定する条件)を添える

## 7. 非機能要件
最低限、以下のカテゴリの有無を意識する(該当しない場合も「対象外」と書く)。
性能 / 可用性・信頼性 / セキュリティ / 拡張性・スケーラビリティ /
運用・保守性 / ユーザビリティ・アクセシビリティ / 移行 / 法令・コンプライアンス。
**目標値は定量で**(例: 「速い」ではなく「95パーセンタイルで 500ms 以内」)。

## 8. 制約条件
予算・期日・利用技術・既存システム・組織ルールなど、設計の自由度を縛るもの。

## 9. 前提条件・仮定(重要)
確証はないが、これを前提に書き進めた事項。**ヒアリングの仮定ログをここに転記**する。
各仮定に「もし誤っていた場合の影響」を一言添えると、後の検証で効く。

## 10. 未決事項・課題管理(重要)
ステークホルダーの判断待ちで埋められなかった点を**残す欄**。
ID / 質問内容 / 必要な決定者 / ブロックする要件 を表で管理する。
**ここを空にするために要件を捏造してはならない。**

## 11. トレーサビリティ
各機能要件 → どのビジネスゴールに紐づくかの対応表。
「必要性」の検証(どのゴールにも紐づかない要件＝過剰)に使う。
