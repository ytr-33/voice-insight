# 基本設計スキル

## Overview

要件定義書を読み、実装前に必要な基本設計書へ落とし込む。ステークホルダー判断が必要な穴を捏造せず、設計判断・根拠・要件IDとの対応を残す。

既定の入力は `documents/10_要件定義/`、既定の出力先は `documents/20_基本設計/` とする。ユーザーが別パスを指定した場合は、その指定を優先する。

## Workflow

1. 入力確認を行う。
   `references/required-inputs.md` を読み、要件定義書・補足資料・既存制約から基本設計に必要な情報を確認する。

2. 質問チェックポイントを置く。
   ステークホルダーにしか決められない事項が残る場合は、基本設計の起草前にユーザーへ質問する。ユーザーが「仮定で進めてよい」と明示した場合だけ、仮定ログへ移して続行する。

3. 文書構成計画を作る。
   `references/document-structures.md` を読み、単一ファイルか複数ファイルかを決める。出力先、ファイル一覧、各ファイルの目的、ID接頭辞、横断ルールを先に固定する。

4. 基本設計書を起草する。
   `references/template.md` と文書構成計画に従い、要件を設計判断へ変換する。設計の選択肢、採用理由、不採用理由、影響する要件IDを明記する。

5. レビューする。
   `references/quality-checklist.md` を読み、要件との対応、設計判断の根拠、画面/API/データ/非機能の整合、未決事項の扱いを採点する。

6. 最大3回まで修正する。
   致命指摘が残る場合は指摘箇所だけを修正し、再レビューする。3回で合格しない場合は、残課題と判断待ち事項を明示して止める。

## References

- `references/required-inputs.md`: 起草前の入力チェック、質問リスト、仮定ログの作り方。
- `references/document-structures.md`: 規模別の基本設計書分割パターン、出力先、IDルール。
- `references/template.md`: 基本設計書の章立てと各章で書く内容。
- `references/quality-checklist.md`: 完成ドラフトの採点基準、重大度、合格条件。
- `references/role-clarifier.md`: 入力確認フェーズの担当手順。
- `references/role-architect.md`: 文書構成計画フェーズの担当手順。
- `references/role-writer.md`: 起草・修正フェーズの担当手順。
- `references/role-reviewer.md`: レビューフェーズの担当手順。

## Guardrails

- 要件定義にない機能や保存方式を、便利そうという理由で追加しない。
- ステークホルダー判断が必要な事項を、もっともらしい設計で埋めない。
- 基本設計で扱うのは実装前の方式・外部設計レベルまでとし、詳細設計や実装コード生成へ踏み込まない。
- 要件ID、設計判断、未決事項、仮定を追跡できる形で残す。
- 対象リポジトリに固有の制約がある場合は、ルートのプロジェクト指示と要件定義書を優先する。
