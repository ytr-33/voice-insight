# 基本設計書の分割パターン

既定の出力先は `documents/20_基本設計/`。規模と複雑さに応じて単一ファイルまたは複数ファイルにする。過剰分割で読みづらくしない。

## 規模の見極め

- 小規模: 単機能、PoC、画面数が少ない、外部連携が少ない。単一ファイルで十分。
- 中規模: 標準的なWebアプリ、複数画面、APIや外部サービス連携がある。4から6ファイルに分ける。
- 大規模: 複数サブシステム、複数ドメイン、多数の外部連携、データモデルが重い。ドメイン単位に分割する。

## 小規模セット

| ファイル | 目的 | ID接頭辞 |
| --- | --- | --- |
| `基本設計書.md` | 全章を1ファイルにまとめる | BD-/DD-/IF-/UI-/NFD- |

## 文書構成計画フォーマット

```
## 規模判断: [小 / 中 / 大]  (根拠: ...)

## 出力先
- <出力ディレクトリまたはファイル>

## 文書構成計画
| ファイル | 目的 | 含む内容 | ID接頭辞 |
| --- | --- | --- | --- |
| ... | ... | ... | ... |

## 横断ルール
- 要件トレーサビリティ集約先: <ファイル>
- 設計判断ログ集約先: <ファイル>
- 前提・仮定・未決事項集約先: <ファイル>
- ID衝突回避方針: <方針>
```

## 分割時の必須ルール

- 要件IDは変更せず、設計IDを追加する。
- 設計IDはファイルをまたいで一意にする。
- トレーサビリティ、設計判断ログ、前提・仮定、未決事項は1か所に集約する。
- 同じ説明を複数ファイルにコピーしない。別ファイルの設計IDを参照する。
- 画面、API、データ、非機能の間で矛盾する状態名・項目名・エラー名を使わない。
