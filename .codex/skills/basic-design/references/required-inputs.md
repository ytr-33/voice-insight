# 基本設計の必要入力チェックリスト

基本設計の起草前に、要件定義書と補足資料に対して以下を `[ある / 曖昧 / 欠落]` で判定する。既定の入力は `documents/10_要件定義/`。

## チェック項目

1. 目的・スコープ・対象外が明確か。
2. 機能要件・画面要件・ユースケースにIDがあり、設計から参照できるか。
3. 非機能要件のカテゴリと目標値があるか。性能、可用性、セキュリティ、運用、法令、アクセシビリティを確認する。
4. 技術スタック、ホスティング、外部サービス、AIモデルなど、方式選定が必要な範囲が分かるか。
5. 画面一覧、画面遷移、主要状態、エラー状態が分かるか。
6. API、外部連携、外部AI連携、入出力データ、タイムアウトや失敗時の扱いが分かるか。
7. データモデル、保存対象、保存しないデータ、一時データの扱い、削除タイミングが分かるか。
8. 認証・認可・ユーザー管理の有無が分かるか。
9. 運用、監視、ログ、デプロイ、環境分離、障害時対応の要件が分かるか。
10. 制約、リスク、承認者、未決事項、後続工程への申し送りが分かるか。

## 穴の分類

### A. 仮定で進めてよい穴

要件本文、業界慣行、既存のプロジェクト指示から合理的に補えるもの。勝手に確定させず、仮定ログに記録する。

各エントリには、仮定した内容、根拠、誤っていた場合の影響、確認すべきタイミングを書く。

### B. 人間に聞くしかない穴

予算、期日、採用する外部サービス、法務・セキュリティ判断、承認者、SLA、保存可否、個人情報の扱いなど、ステークホルダーにしか正解がないもの。起草前に質問として残す。

### C. 詳細設計以降に送る穴

基本設計で方針だけ決めればよい実装詳細。後続工程への申し送りとして残し、基本設計書では決めない理由を明記する。

## 出力フォーマット

```
## 入力充足度サマリ
- 充足: N項目 / 曖昧: N項目 / 欠落: N項目
- 基本設計の起草可否: [可 / 質問回答後に可 / 不可]

## 人間への質問リスト
- Q1. <質問> / 必要な決定者: <誰> / ブロックされる設計範囲: <範囲>

## 仮定ログ
- AS1. 仮定: <内容> / 根拠: <根拠> / 誤りだった場合の影響: <影響> / 確認タイミング: <時期>

## 後続工程への申し送り
- DS1. <詳細設計以降で決める内容> / 基本設計で決めない理由: <理由>
```

起草可否が「質問回答後に可」または「不可」の場合は、基本設計書本文を書かず、質問提示で止める。
